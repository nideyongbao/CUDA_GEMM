# 性能分析方法论（ncu 三板斧）

本项目用一套固定的 ncu 流程分析每个 CUDA core kernel：**看大局 → 看延迟 → 看访存合并/bank**。各 kernel 的实测结果见 docs 02–07。

> **H20 上跑 ncu 的两个前提**（本机已踩过坑）：
> 1. GPU 性能计数器需 root → 用 `sudo`；
> 2. `sudo` 会重置 PATH，root 找不到 `ncu` → 必须写**全路径** `/usr/local/cuda/bin/ncu`。
>
> 所以本机所有命令都是 `sudo /usr/local/cuda/bin/ncu ...`。下文以 double_buffer（id 12）和 naive（id 1）为例；换 kernel 改 `-k regex` 和 `bench <id>` 即可（当前 bench id：1 naive / 2 smem / 3 blocktiling / 4 2D / 5 vectorized / 9 warptile / 10 warptile_vec / 11 bank_conflict / 12 double_buffer）。`--launch-count 1` 只剖析第一次 launch。

## 1、先看大局
``` text
sudo /usr/local/cuda/bin/ncu --set basic -k regex:"double" --launch-count 1 \
  ./build/cuda_core/bench 12 4096 4096 4096
```

| 指标                 | 看什么                              |
| ------------------ | -------------------------------- |
| Duration           | kernel 实际跑多久                     |
| Compute Throughput | SM 计算管线忙不忙                       |
| Memory Throughput  | memory 系统整体忙不忙                   |
| DRAM Throughput    | 显存带宽忙不忙                          |
| L1/TEX Throughput  | L1/shared/TEX 片上 memory path 忙不忙 |
| L2 Throughput      | L2 cache 路径忙不忙                   |

> 判读要点：`Compute (SM)` 取计算子管线最忙的一档、`Memory` 取访存子管线最忙的一档。当二者约等且都约等于 `L1/TEX` 时（naive 即如此），不是"算力带宽双满"，而是同一条 LSU/L1 管线同时顶进两个口径。真正看显存压力要看 `DRAM Throughput`——本项目在 H20 上它**从不高**（4TB/s + 60MB L2）。

## 2、再看延迟
``` text
sudo /usr/local/cuda/bin/ncu --section WarpStateStats \
  --metrics \
smsp__average_warps_issue_stalled_long_scoreboard_per_issue_active.ratio,\
smsp__average_warps_issue_stalled_short_scoreboard_per_issue_active.ratio,\
smsp__average_warps_issue_stalled_math_pipe_throttle_per_issue_active.ratio,\
smsp__average_warps_issue_stalled_mio_throttle_per_issue_active.ratio,\
smsp__average_warps_issue_stalled_barrier_per_issue_active.ratio \
  -k regex:"double" --launch-count 1 ./build/cuda_core/bench 12 4096 4096 4096
```

| 指标                                       | 说明                                    |
| ---------------------------------------- | ------------------------------------- |
| Warp Cycles Per Issued Instruction       | 单个 warp 平均隔多少 cycle 才能 issue 指令       |
| Warp Cycles Per Executed Instruction     | 单个 warp 平均隔多少 cycle 才执行指令             |
| Avg. Active Threads Per Warp             | 每条 warp 指令平均活跃线程数                     |
| Avg. Not Predicated Off Threads Per Warp | 没被 predicate 屏蔽的线程数                   |
| long_scoreboard                          | 等 global / local / texture 路径 load 数据 |
| math_pipe_throttle                       | math pipe 忙，数学指令发不进去                  |
| mio_throttle                             | MIO 队列 / 管线忙（LDS / 访存指令排队）           |
| short_scoreboard                         | 等 shared memory / MIO 结果              |

> 经验对照（H20 实测）：naive 是 `long_scoreboard` 主导（等 global）、smem 转成 `mio_throttle` 主导（LDS 塞爆）、register tile 之后 `cyc/issue` 从 ~44 砍到 ~8、各项 stall 都降到很低。

``` text
 sudo /usr/local/cuda/bin/ncu --section SchedulerStats -k regex:"naive" --launch-count 1 ./build/cuda_core/bench 1 4096 4096 4096
```

| 指标                           | 含义                            |
| ---------------------------- | ----------------------------- |
| Active Warps Per Scheduler   | 每个 scheduler 上有多少 active warp（H20 上限 **16**） |
| Eligible Warps Per Scheduler | 每个 scheduler 上有多少 ready warp  |
| One or More Eligible         | 有至少一个 ready warp 的周期比例        |
| No Eligible                  | 没有任何 ready warp 的周期比例（越高越空转）  |
| Issued Warp Per Scheduler    | 每周期实际发射多少 warp 指令             |

## 3、再看访存合并、bank conflict
``` text
sudo /usr/local/cuda/bin/ncu --metrics \
l1tex__average_t_sectors_per_request_pipe_lsu_mem_global_op_ld.ratio,\
l1tex__average_t_sectors_per_request_pipe_lsu_mem_global_op_st.ratio \
-k regex:"naive" --launch-count 1 ./build/cuda_core/bench 1 4096 4096 4096
```
ld 就是读，value 单位是 sector，一个 sector 是 32 byte，32 个线程连续读 float 是 4×32=128 byte = 4 sectors，所以一次 ld 指令最好就是 4；st 就是写，同理。低于 4 是广播、高于 4 是不合并（地址散）。

``` text
sudo /usr/local/cuda/bin/ncu --metrics \
l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum,\
l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_st.sum \
-k regex:"naive" --launch-count 1 ./build/cuda_core/bench 1 4096 4096 4096
```
看 shared memory 读/写有没有 bank conflict（naive 没用 smem → 全 0）。

> **判优先级的铁律**：一个瓶颈在 ncu 上"指标高/计数大"不代表它在关键路径上。判它值不值得打，看消除后 `Duration` / `Elapsed Cycles` 降不降。本项目 07 就有反例：bank conflict 砍 4× 但 throughput 不升反略降（H20 上它非 binding）。

``` text
sudo /usr/local/cuda/bin/ncu --section Occupancy \
    --section LaunchStats \
-k regex:"naive" --launch-count 1 ./build/cuda_core/bench 1 4096 4096 4096
```
看 Occupancy（占用率）与 Launch 配置（grid/block、Registers Per Thread、Block Limit）。注意：**占用率不是越高越好**——本项目最快的 double_buffer 占用率只有 24%，靠 ILP 而非 TLP 隐藏延迟。
