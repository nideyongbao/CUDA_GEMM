# H20 结果分析 & FP8 利用率口径修正

> 结论先行：**H20 的 FP8 数字（226 TFLOPS）从头到尾都是对的**，错的只是汇总报告里那一行的**利用率口径**——它拿 FP8 的吞吐去除以 **BF16** 的峰值，于是算出「**152.7% 峰值**」这种物理上不可能的数。修正后 FP8 = **76.4% 的 FP8 峰值（296T）**。本文说明问题、根因、修法与修正后的完整数字。

---

## 1. 现象：一个 >100% 的「超越物理峰值」

修正前 `result/20260701_150344_both/locked/00_summary.md` 的张量核表与关键数字：

```
| tc_05 WGMMA_fp8 | 226051 | 152.7% |   ← %BF16峰值，>100%，不可能
手写张量核最佳: 226.1 TFLOPS（153% BF16峰值）   ← 同样的错
```

任何 kernel 的实测吞吐都不可能超过它所用精度的物理峰值。出现 153% 只有一种可能：**分母用错了峰值**。

## 2. 根因：汇总器把 FP8 当成了 BF16

关键证据——**kernel 自己打印的原始 bench 日志本来就是对的**
（`result/20260701_150344_both/locked/bench/tensor_core/05_tc05_wgmma_fp8_4096.log`）：

```
[tc_05 WGMMA_fp8] M=4096 N=4096 K=4096  time=0.6080 ms  GFLOPS=226050.92  util(vs296T)=76.4%  util(vs148T)=152.7%
```

kernel 同时给了两条参考线：对 **FP8 峰值 296T** 是 **76.4%**，对 **BF16 峰值 148T** 是 152.7%。
旧版 `scripts/gemm_summary.py` 只 `grep` 了 `GFLOPS=`，然后对**所有**张量核行**一律套 BF16 峰值**——于是恰好选中了那条错误的 152.7%。

- H20（Hopper）FP8(e4m3) 张量核峰值 = **2× BF16** = 148×2 = **296 TFLOPS**（dense，FP32 累加）。
- FP8 GEMM 的 GFLOPS 定义仍是 `2·M·N·K/t`（数的是 FLOP，与精度无关）；FP8 的优势是**同样的 FLOP 跑得更快**（张量核吞吐翻倍）。所以 226T 合理地高于 BF16 路径，是**真实**的，不是错误。

**一句话根因**：`gemm_summary.py` 只有一个 `BF16_PK`，套给了包括 FP8 在内的每一行张量核用例，也套给了「手写张量核最佳」。

### 附带发现：FP32 峰值一列全是 `-`
旧报告顶部还有 `SM 数: None` / `理论峰值: 未知`。原因是汇总器用 `torch` 读 SM 数，而本机 **torch 2.11+cu130 与驱动 12.8 版本不匹配**，`torch.cuda` 初始化直接抛异常 → SM=None → FP32 峰值算不出来。C++ 的 bench/verify 走 CUDA runtime 完全正常，所以只有这个 Python 汇总步骤受影响。

## 3. 修法：把「设备算力事实」抽成单一真源

新增 **`scripts/gpu_specs.py`**（对齐 `platform/benchmarks/gpu_specs.py` 的思路）作为全仓库唯一的算力表：

- **只手工维护一张 BF16 dense 峰值表**；`FP8 = 2×BF16`、`FP4 = 4×BF16` 都按**计算能力(CC)推导**，不再逐卡手填。
- 精度支持**按 CC 判定，不按卡名**：FP8 仅 Ada(8.9)/Hopper(9.0)/Blackwell(10+)；FP4 仅 Blackwell；Ampere(8.0/8.6) **无 FP8**。
- **SM 数兜底表**（torch 不可用时用）：H20=78（ncu 实测确认）、A800/A100=108、A10=72、A10G=80、L4=58 …
- 卡名按**长度降序**匹配，避免 `H20⊂H200`、`A10⊂A100/A10G`、`L4⊂L40S` 误命中。

`gemm_summary.py` 改动：
1. SM 数：先试 torch，失败退回 `gpu_specs.sm_count(name)`（本机 → 78）。
2. 张量核表每行**按精度选峰值**：`peak_for_label(label)` — 含 `fp8`→FP8 峰值、`fp4`→FP4 峰值、否则 BF16。表里新增「精度」列。
3. 「手写张量核最佳」拆成 **BF16 路径** 与 **FP8 路径** 两行，各对自己的峰值报 MFU；且排除内嵌的 `cuBLAS fair` 参考行（它不是手写 kernel）。

## 4. 修正后的 H20 完整数字（`--lock` @1980MHz，实测计算期 ~1830MHz）

| 口径 | GFLOPS/TFLOPS | 峰值基准 | 利用率 |
| --- | ---: | --- | ---: |
| FP32 cuBLAS | 28.0 T | FP32 39.5T | 70.9% |
| FP32 手写最佳(double_buffer) | 23.2 T | — | 83% cuBLAS |
| BF16 cuBLAS(fair) | 134.0 T | BF16 148T | 90.5% |
| **手写张量核最佳 · BF16 路径**(tc_04 WGMMA) | **120.6 T** | BF16 148T | **81.5%** |
| **手写张量核最佳 · FP8 路径**(tc_05 WGMMA_fp8) | **226.1 T** | **FP8 296T** | **76.4%** ✅ |

- FP8 的 226T ≈ 168.7% of cuBLAS-BF16（合法的**比值**：FP8 比 BF16 库实现快 1.69×），也 ≈ 153% of BF16 峰值——但**报利用率必须对 FP8 峰值**，否则就是拿苹果的产量去除以橙子的上限。
- 峰值口径说明：FP32 峰值按「SM×128×2×额定1980MHz」= 39.5T（额定上限）；实测计算期锁在 1830MHz，故各 %峰值略偏保守，属已知时钟口径（见报告末「时钟提示」）。

## 5. FP8 正确性是真的吗？是。

`tc_05` 没有简单 cuBLAS 路径，用 **CPU double 参考**（解码同一份 fp8 输入做双精度累加）在 ≤512³ 上对拍，判据 `|误差| > 0.1 + 5%·|真值|` 计为 bad：

```
[tc_05 WGMMA_fp8] VERIFY(512^3, vs CPU double) max_abs=2.927e-02 bad=0/262144  PASS
```

262144 个元素 0 个越界 → FP8 数值正确性成立（e4m3 每元素 ~6% 相对误差，K 维累加后仍在这个宽容差内）。

## 6. 对 A800 的交叉验证

同一套修正下，A800（Ampere sm_80，`result/20260701_065155_both`）汇总**正确地没有 FP8 行、也没有 FP8 峰值**——因为 Ampere 没有 FP8 张量核（`gpu_specs.supports_fp8(8.0)=False`），且 `TC_HOPPER=0` 只编译 WMMA tc_01–03。这反过来证明「按 CC 门控精度」是对的：

```
===== GEMM 汇总: NVIDIA A800-SXM4-80GB (CC 8.0, 108 SM) =====
峰值: FP32 19.5T | BF16 312T            ← 无 FP8
手写TC(BF16)最佳 43.1T (14%峰)          ← Ampere 止步 WMMA
```
