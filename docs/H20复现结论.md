# H20 复现结论

> ⚠️ **本文是早期逐步复现的详细记录。**项目后来按引擎重构了目录、并把 tensor core 用例拆成独立最简用例、补了 FP8 与全量 ncu 剖析。**最终收敛结论请看 [13 H20 GEMM 复现总结](13%20H20%20GEMM%20复现总结.md)。**
> 结构变化：原 §6 里 bench_bf16 的 id 13/14/15(WMMA) 与独立的 bench_wgmma，现已迁移为 `kernels/tensor_core/tc_01..tc_05`（含新增 FP8），逐例分析见 docs 08–12。下文内容除此结构差异外仍然有效。

## 2、为适配 H20 做的改动

1. `Makefile`：`ARCH` `sm_75` → **`sm_90a`**（Hopper 原生目标；`sm_75` 在 H20 上靠 PTX JIT 也能跑，但非原生调优、性能不可信）。
2. `src/benchmark.cu` / `src/verify.cu`：修正 kernel 名字注册表（`dummy_kernel`→`cublas_ref`，`"7"/"8"`→`autotune_64x64x16_8x4` / `autotune_64x64x8_8x8`），输出标签与 id 对齐。
3. `src/verify.cu`：误差判据改为 numpy `allclose` 风格 `|a-b| <= atol + rtol*|b|`（atol=rtol=1e-2），消除随机数据下近零元素的假 FAIL。
4. `docs/00`：硬件参数更新为 H20 实测值（替换 `GDDR5 ~128GB/s` 占位）。
5. 新增 `.gitignore`（忽略 `*.o`、`bench`/`verify`、`*.ncu-rep`）。

## 3、正确性（vs cuBLAS，allclose atol=rtol=1e-2）

全部 13 个 kernel 在 **1024³ 与 2048³ 均 PASS**。

| 尺寸 | 全部 kernel max_abs_err | bad_count | 结论 |
| --- | --- | --- | --- |
| 1024³ | 0.0（巧合，见下） | 0 | PASS |
| 2048³ | 1.91e-04 | 0 | PASS |

**关于 1024³ 的 “0.0” —— 不是 bit-exact 的普遍规律，而是巧合：**
- 独立用 CPU double 累加做参考：`naive vs CPU ≈ 3.4e-5`，`cuBLAS vs CPU ≈ 1.9e-5`，量级一致 → kernel 计算本身是对的。
- 1023/1024/1025 这几个尺寸下 cuBLAS 恰好选了与手写 kernel **相同 k 累加顺序**的实现，于是 bit 级相同（误差 0.0）；768/1280/2048 下 cuBLAS 换了实现，出现正常的 ~1e-4 FP32 累加顺序差异。
- 2048³ 下所有手写 kernel 的误差**完全相同**（1.907349e-04），印证它们都按 `k=0..K-1` 同序累加，只是与 cuBLAS 的顺序不同。
- 旧的 `abs OR rel` 判据在近零的 C 元素上会因相对误差爆炸（max_rel 可达 ~1.0）造成假 FAIL；改 allclose 后消失。

## 5、复现结论要点

1. **优化阶梯成立**：4096³ 上 naive→double_buffer 提升约 **7.1×**（3532→25116 GFLOPS），与文档叙事一致。
2. **double_buffer 是最强手写 kernel**：达到 fair cuBLAS SGEMM 的 **83%**，约 FP32 峰值的 57%。
3. **warptile 标量版（id 9）是真实负优化**：12794 GFLOPS，反而低于更早的 vectorized（22770）；只有配上 float4 的 warptile_vec（id 10, 23962）才追回并超过。这是“某步优化何时无效”的好教材。
4. **cuBLAS handle 开销假象（已修复）**：原 `launch_cublas_ref`/`launch_cublas_bf16_ref` 在**每次计时调用内部** `cublasCreate/Destroy`，固定开销约 **0.33ms/次**。在小/中尺寸上这会把 cuBLAS 严重低估，制造"手写超过 cuBLAS"的假象：
   - FP32 SGEMM 1024³：5204 →（handle 复用后）**22895** GFLOPS；4096³：28222 → **30264**。
   - BF16 4096³：68.4% → **89.3%**；2048³：23.4% → **80.0%**；8192³ 几乎不变（GEMM 时间远大于 handle，89%→93%）。
   现已把 handle 改为只创建一次（`static` 单例）。**结论修正：fair 测量下 cuBLAS 在所有尺寸都快于手写 kernel；之前任何"手写反超 cuBLAS"的说法都是该假象所致。** 这也是 benchmark 方法论的典型坑：固定开销务必移出计时循环。
5. **更大 tile 不一定更快**：autotune 中 128x128x8_8x8 反而最慢（occupancy / 寄存器压力）。
6. **正确性可靠**：13 个 kernel 全部通过，且已用 CPU double 参考独立交叉验证。

## 6、BF16 全量复现（对 148 TFLOPS Tensor Core 峰值的利用率）

新增 BF16 套件：`include/bf16.h` + `kernels/bf16_kernels.cu`（全部 13 个 kernel 的 BF16 版 + 2 个 WMMA tensor core kernel），harness 为 `src/bench_bf16.cu` / `src/verify_bf16.cu`，参考为 cuBLAS BF16（`cublasGemmEx`，bf16 输入 / FP32 累加）。设计：**A/B 存 bf16，载入转 FP32，smem/寄存器/累加全程 FP32，C 输出 FP32**；CUDA-core kernel 的计算循环与 FP32 版逐行一致，只换 global load。

**正确性**：15 个 kernel 在 1024³/2048³ 全部 PASS。CUDA-core 版误差全部相同（如 1024³ 下 9.92e-05），印证同序累加；两个 WMMA 与 cuBLAS BF16 **bit 级相同**（0.0）。

### 手写 Tensor Core 阶梯：cp.async 多级流水线值多少

| 步骤 | kernel | 关键改动 | GFLOPS | util | 相对上一步 |
| --- | --- | --- | ---: | ---: | ---: |
| ① 朴素 TC | WMMA_naive | 直接从 global 取 fragment | 16657 | 11.3% | — |
| ② smem staging | WMMA_smem | tile 搬进 smem 复用（64×64，同步） | 27934 | 18.9% | +68% |
| ③ 异步流水线 | WMMA_pipe | 更大 tile(128×64) + cp.async 3 级 ring buffer 预取，搬运/计算重叠 | 37815 | 25.6% | +35% |
| ④ **WGMMA** | **bench_wgmma** | **TMA 异步搬运 + warpgroup 异步张量指令 wgmma.mma_async + warp specialization + 3 级流水线** | **119353** | **80.6%** | **×3.1** |
| 参考 | cuBLAS BF16 (fair) | 完整 Hopper 流水线 | 132145 | 89.3% | — |

第③步（`kernels/bf16_kernels.cu` 的 `wmma_pipe_bf16_kernel`，id 15）是”异步搬运”的直接体现：smem 改成 3 级 ring buffer，用 `cp.async`(`__pipeline_memcpy_async` + `commit` + `wait_prior`) 预取后续 K-tile，让”搬下一块”和”算当前块”跑在不同硬件上重叠。它**正是 Hopper TMA + mbarrier 多级流水线的同步原语版前身**：cp.async 对应 TMA、commit/wait_prior 对应 mbarrier 的 phase 等待（参考 `modern-gpu-programming-for-mlsys` 的 *Async GEMM*/*mbarriers* 两章，结构完全一致）。

第④步（`src/bench_wgmma.cu`，独立可执行 `bench_wgmma`）换上 **Hopper 原生 WGMMA**：`wgmma.mma_async.m64n128k16.f32.bf16.bf16` 由 **warpgroup(128 线程)** 异步发射、操作数**直接从 shared memory 取**（descriptor 描述 128B-swizzle 布局），配 **TMA**(`cp.async.bulk.tensor`，descriptor 化批量异步搬运)、**mbarrier**(`cuda::barrier`，expect_tx 字节计数)、**warp specialization**(1 个生产者 WG 跑 TMA、1 个消费者 WG 跑 WGMMA)与 3 级流水线。这是手写路线的质变：**25.6% → 80.6%（×3.1）**，达到 fair cuBLAS BF16 的约 **90%**。利用率随规模上升：手写 WGMMA 2048³ 65.6% / 4096³ 80.6% / **8192³ 88.2%（130 TFLOPS）**，同 harness 下 fair cuBLAS 为 79.9% / 89.3% / 92.9% —— cuBLAS 仍稳定领先，但这个极简手写 kernel 已逼到它的九成。

> 一个关键认识：**WGMMA 没法和 TMA/swizzle 拆开单独”最小化”**——它的 smem 操作数必须是 TMA 产出的 128B-swizzle core-matrix 布局，描述符魔数也和这套布局绑死。所以”最小 WGMMA”实际就是 TMA+WGMMA 这一对，这本身就是 Hopper “异步硬件协同设计”的体现。本 kernel 移植自已验证正确的 LeetCUDA `hgemm_wgmma_fp32acc_stages_tn`，改 bf16 + 适配本项目 row-major（内部把 B 转置成 N×K 一次，不计时）。

### 关键结论

1. **只把数据类型换成 BF16，对 CUDA-core kernel 基本无加速**（±几个百分点）：GEMM 在这些 kernel 上是 **FP32 计算单元 bound**，BF16 只省一半 global 访存而那不是瓶颈；转换偶尔还反噬（naive −9%）。CUDA-core 全量天花板只有 **~17-18%**。
2. **用 Tensor Core 必要但不充分**：朴素 WMMA（11.3%）甚至比最好的 CUDA-core kernel（17.5%）还慢——直接从 global 取 fragment，被访存卡死、喂不饱张量核。
3. **手写 tensor core 阶梯 11% → 19% → 26%**：smem 复用 +68%，再加 **cp.async 异步流水线 +35%**。异步是真金白银：同样的 WMMA 数学，靠”搬运/计算重叠”就再榨出三成。
4. **换上 Hopper 原生指令(WGMMA+TMA+warp specialization)实现质变**：cp.async+WMMA 这条 Ampere 风格的路到 25.6% 见顶；换成 `wgmma.mma_async`(warpgroup 异步、操作数直接吃 smem) + TMA + WS 后直接到 **80.6%（×3.1），8192³ 达 88%**，逼到 fair cuBLAS 的约九成。这就是"warpgroup 异步张量指令值多少"的答案 —— 它和 warp 级 WMMA 不是同一个量级。
5. **BF16 计算利用率小结（fair）**：CUDA-core 全量 ~2–18%，手写 WMMA(warp 级) ~11–26%，**手写 WGMMA(warpgroup+TMA+WS) ~66–88%**，**cuBLAS BF16 ~80–93%**（仍是最快）。
6. **cuBLAS 不是"被反超"，而是之前测量不公**：见 §5，handle-per-call 把 cuBLAS 严重低估；修正后 cuBLAS 在所有尺寸都领先，手写 WGMMA 逼到其 ~90%。

用法：`make`（默认含 bf16 目标）→ `./bench_bf16 <id> M N K`（带 util%）/ `./verify_bf16 <id> M N K`。

## 7、Hopper 定位

本项目从**纯 FP32 + CUDA core** 的 SGEMM 起步（FP32 峰值 57%），一路走到 **Hopper 原生 WGMMA**，已把手写 tensor core GEMM 推到 H20 BF16 峰值（148 TFLOPS）的 **80.6%（4096³）/ 88.2%（8192³）**，达到 fair cuBLAS BF16（89% / 93%）的约九成。整条复现链已经打通。

定位与进度：
- ✅ CUDA core 全套（naive → double_buffer，FP32 峰值 57% / BF16 峰值 ~17%）
- ✅ Tensor core warp 级：WMMA（朴素 / smem / cp.async 多级流水线，11% → 19% → 26%）
- ✅ Tensor core warpgroup 级：**WGMMA + TMA + warp specialization + 多级流水线**（`bench_wgmma`，**80.6% / 88.1%**）
- ⬜ 仍可继续：smem swizzle 自己写（当前靠 TMA 产生）、persistent kernel + tile scheduler、cluster/DSMEM (2-CTA)、不同形状(瘦长/小 M)的 SwapAB 与调度，以及用 CuTe/CUTLASS 把这套表达得更干净。

参考资料：`/shard_data/brooksli/workspace/0625/modern-gpu-programming-for-mlsys`（*Tiled to SOTA* 的 TMA pipelining / warp specialization / 2-CTA cluster 章节正好覆盖剩余路线，载体是 TIRx DSL）；WGMMA kernel 移植自 LeetCUDA `hgemm_wgmma_fp32acc_stages_tn`。
