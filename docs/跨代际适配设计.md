# 跨代际 GPU 适配设计（Ampere sm_86 / Ada sm_89 / Hopper sm_90 / Blackwell sm_100）

> 目标：让这套原本围绕 **H20（Hopper）** 写的 GEMM 阶梯，能一条命令跑在任意代际的 NVIDIA 卡上，
> 且**报告口径统一、精度门控正确、kernel 源码零改动**。本文是「怎么设计、改了什么、再加一张卡要动哪」。

---

## 1. 一句话设计：把「三件会随卡变的事」各自收敛到一个地方

移植一个手写 CUDA GEMM 仓库到新架构，真正会变的只有三类东西。本仓库把它们**各自收敛到单一位置**，互不耦合：

| 会变的东西 | 收敛到哪 | 谁消费 |
| --- | --- | --- |
| **① 编译目标** `-arch=sm_XX` | `run_all.sh` 的 CC→arch 矩阵（`Makefile ARCH` 兜底） | nvcc |
| **② 张量核指令可用性**（哪几级 kernel 能编/能跑） | `run_all.sh` 的 `TC_MAX` + `Makefile` 的 `TC_HOPPER`/`-DNO_HOPPER` 派发表门控 | make / bench 驱动 |
| **③ 算力事实**（峰值 TFLOPS、SM 数、精度支持） | **`scripts/gpu_specs.py`（唯一真源）** | `gemm_summary.py` 算 MFU |

**换代际 = 改这几张表，不碰 `kernels/`**。只有当你要用**新指令**打满新卡（见 §5）时，才需要新增 kernel。

---

## 2. 架构自适应矩阵（已实现于 `run_all.sh` / `Makefile`）

`run_all.sh` 用 `nvidia-smi --query-gpu=compute_cap` 读到 CC，查下表决定编什么、跑到第几级：

| 代际 | CC | `-arch` | `TC_HOPPER` | `TC_MAX` | 能跑的张量核用例 | 代表卡 |
| --- | --- | --- | :--: | :--: | --- | --- |
| Volta/Turing | 7.x | `sm_75/70` | 0 | **0** | 无（无 bf16 WMMA）→ 只跑 CUDA core | T4/V100 |
| Ampere-数据中心 | 8.0 | `sm_80` | 0 | 3 | tc_01–03 WMMA | A100 / A800 |
| Ampere-图形 | 8.6/8.7 | `sm_86` | 0 | 3 | tc_01–03 WMMA | **A10 / A10G** / A40 |
| Ada Lovelace | 8.9 | `sm_89` | 0 | 3 | tc_01–03 WMMA（\*） | **L4** / L40S / 4090 |
| Hopper | 9.0 | `sm_90a` | **1** | **5** | tc_01–05（+WGMMA/TMA/FP8） | **H20** / H100 / H200 |
| Blackwell | 10.x/12.x | `sm_100/120` | 0 | 3 | tc_01–03 WMMA（\*\*） | B200 / RTX50 |

- **张量核阶梯**：`tc_01-03` 是 **WMMA**（bf16 输入 / f32 累加，`sm_80+` 通用）；`tc_04` 是 **WGMMA+TMA+warp specialization**、`tc_05` 是 **FP8 WGMMA**——后两者是 **Hopper `sm_90` 独占指令**，靠 `TC_HOPPER=1` 打开、`-DNO_HOPPER` 从派发表 `tc_cases.h` 剔除。
- **(\*) Ada 有 FP8 硬件，但本仓库的 FP8 kernel 走的是 Hopper 独占的 `wgmma.mma_async ... e4m3` 指令**，Ada 上跑不了 → 只跑到 WMMA。要在 Ada 上测 FP8 需另写 `mma.sync` 版本（§5）。
- **(\*\*) Blackwell** 的 WGMMA 已被 `tcgen05`/UMMA 取代，并新增 FP4——现有 WGMMA kernel 不适用，故暂只跑通用 WMMA（§5）。`sm_90a` 的后缀 `a`=architecture-specific，是 Hopper 指令的硬性要求；Blackwell 同理有 `sm_100a`。

`sm_86/sm_89` 上「只跑 WMMA、不谎报 FP8」正是**正确**行为——精度门控见 §3。

## 3. 算力事实的单一真源：`scripts/gpu_specs.py`

对齐 `platform/benchmarks/gpu_specs.py` 的做法，全仓库**只手工维护一张 BF16 dense 峰值表**，其余推导：

```python
FP8 峰值 = 2 × BF16      # 当代际支持 FP8 时（Ada 8.9 / Hopper 9.0 / Blackwell 10+）
FP4 峰值 = 4 × BF16      # 仅 Blackwell
FP32 峰值 = SM × (FP32 lane/SM) × 2 × 额定boost频率
```

**精度支持按计算能力(CC)判定，不按卡名**——这条是 FP8 口径修正的关键（详见
[FP8 利用率口径修正](h20/FP8-利用率口径修正与H20结果分析.md)）：

| 能力 | 判据 | 说明 |
| --- | --- | --- |
| `supports_bf16_tc` | CC ≥ 8.0 | Turing/Volta 无原生 bf16 |
| `supports_fp8` | CC == 8.9 或 major ≥ 9 | **Ampere(8.0/8.6) 没有 FP8** |
| `supports_fp4` | major ≥ 10 | Blackwell 独占 |
| `supports_wgmma_tma` | major == 9 | 本仓库 tc_04/tc_05 依赖 |

于是 `gemm_summary.py` 给每个张量核用例**按精度选峰值**：FP8 用例对 296T（H20）算利用率，而不是错误地对 148T 算出「153% 峰值」。Ampere 卡则**根本不会出现 FP8 行**（`supports_fp8(8.0)=False` + `TC_MAX=3`），自证门控正确。

> 自检：`python3 scripts/gpu_specs.py "NVIDIA L4" 8.9 2040` 会打印 L4 的 SM/各精度峰值/是否支持 FP8。

## 4. 移植改造清单

**已完成（本次）**
- ✅ `scripts/gpu_specs.py`：新增，CC 门控 + 峰值 + SM 兜底表（H20/A100/A10/A10G/L4/L40S/H100/H200/B200…）。
- ✅ `run_all.sh`：CC→arch/`TC_MAX` 矩阵显式化（原来靠 `*` 兜底，现在每代际一行且有注释）；`TC_MAX=0` 时跳过张量核编译，避免 Turing 上 bf16 WMMA 编译失败拖垮整轮。
- ✅ `Makefile`：头部注释补全五代际矩阵。
- ✅ `gemm_summary.py`：按精度选峰值 + torch 不可用时退回 `gpu_specs` 兜底 SM 数。
- ✅ `modal/run_gemm.py`：云端一键在任意代际卡上跑（见 [Modal 入口](../modal/README.md)）。

**再加一张「已有代际」的新卡**（如 L40S、A40、H100）：通常**只改 `gpu_specs.py` 一行**——加它的 BF16 峰值与 SM 数即可，arch/门控自动命中矩阵。

**接入一个「全新架构」**（如 Blackwell 真正打满）：
1. `gpu_specs.py` 加峰值/SM（若新卡名）；`run_all.sh` 矩阵加/改一行 arch。
2. 若要用新指令：`kernels/tensor_core/` 加 `tc_06_xxx.cu`，在 `tc_cases.h` 用新的 `#ifdef` 门控进派发表，`Makefile` 加编译分支与链接旗标，`run_all.sh` 提高该代际的 `TC_MAX`。

## 5. 各代际「打满」还缺什么 kernel（诚实的边界）

现有手写阶梯是**为 Hopper 写的**。在别的代际上它能**跑通、能对拍、能给出 WMMA 数字**，但要逼近各代际的**架构上限**还需补 kernel：

| 代际 | 现状（本仓库手写能到） | 打满还需要 |
| --- | --- | --- |
| Ampere sm_80/86 | WMMA tc_03（A800 实测 ~43T，14% of 312T） | Ampere 上 cuBLAS 已达 85–94% 峰；手写要接近需 `cp.async` 多级 + 更大 warptile（Ampere 无 WGMMA，天花板本就靠 TLP）。 |
| Ada sm_89 | WMMA（L4/L40S） | **FP8 需 `mma.sync.aligned...e4m3`**（Ada 的 FP8 走同步 MMA，不是 WGMMA）。 |
| Hopper sm_90 | **完整**：WGMMA+TMA+FP8（H20 tc_04 82%、tc_05 76% of FP8 峰） | 已是本仓库的主线，基本到位。 |
| Blackwell sm_100 | WMMA（兼容跑通） | **`tcgen05`/UMMA** 新张量指令 + **FP4(e2m1)** kernel + `sm_100a`；WGMMA 在 Blackwell 上已非最优路径。 |

所以：**跨代际「能跑、口径对、不谎报」现在就成立**；**跨代际「打满上限」是每代补一个 kernel 的持续工作**——这也是为什么报告用 `gpu_specs` 明确标注每一档的峰值，好让「手写到了百分之几」一目了然。

## 6. 与 `platform` 仓库的分工

| | 本仓库（CUDA_MATMUAL） | platform |
| --- | --- | --- |
| 测什么 | **手写 kernel** 能写到多少（教学阶梯 naive→WGMMA→FP8） | **库/框架**能到多少（`torch.matmul` / `_scaled_mm` / FA / cutlass） |
| 语言 | CUDA C++ + nvcc | PyTorch / Triton / CUTLASS-DSL |
| 精度覆盖 | FP32 / BF16(cuda&TC) / FP8(Hopper) | BF16 / FP8 / FP4 / attention / memory / IO / P2P |
| 峰值口径 | `scripts/gpu_specs.py` | `benchmarks/gpu_specs.py` |

两张 `gpu_specs` 表**数值口径一致**（BF16 dense、FP8=2×、FP4=4×），因此两个仓库在同一张卡上的 MFU 可直接横向对照：platform 的 FP8「库能到 X%」与本仓库的 FP8「手写到 Y%」拼在一起，就是「这张卡 FP8 的库上限 vs 手写差距」。
